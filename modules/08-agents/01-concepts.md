# Lesson 8.1: An agent is part of a workflow, not a complete operating model

[Module route](README.md) · [Next lesson](02-code-workshop.md)

A fixed workflow can always look up an order before preparing a note. An agent can select the next permitted step based on the information returned so far. If the agent can ask for a carrier record, that does not entitle it to issue a credit. List which steps the software can take and which decisions Harbour still assigns to a person.

## The promise of handling the whole request

Harbour's assistant can gather evidence and suggest a route. The next proposal is to let it select the next step: look up another record, ask for clarification, recommend an outcome and prepare a handoff. This is where people often start speaking about an “agent”.

The term is used broadly. In this curriculum, inspect the actual control: what observations are available, what state is retained, who selects the next step and which actions can execute. A class called `Agent` does not answer those questions by itself.

## Fixed workflows and model-selected steps

A **fixed workflow** might always gather an order, retrieve policy, check required evidence and draft a handoff. Python specifies the order. A model can still interpret text at a bounded stage.

Suppose dispatch has a record but the carrier does not. One fixed design can always check both sources. An agent can choose whether the second lookup is useful after seeing the first result, subject to the application's rules. Both designs must stop short of a credit when Harbour has only granted permission to read. The difference is who chooses the next step, not who owns the final decision.

An **agent loop** can ask a model to choose among permitted tools repeatedly. Its next action depends on what it has observed. That flexibility may be useful when requests genuinely require different paths. It also expands the possible sequences you must test and supervise.

A **state machine** represents named states and allowed transitions. For example, `received`, `evidence_ready`, `proposed`, `approved` and `executed`. It is especially useful when work pauses for a person, resumes after failure or must prevent an action before authorisation. Model-selected steps can exist within such a structure; these designs are not mutually exclusive.

## Capability is different from authority

A tool can technically create a credit. Whether an application should be allowed to call it for this request is a business authority question. The execution boundary should use trusted identity, relevant state and policy, not simply a model's confidence.

Narrow tool interfaces help. A tool accepting an approval-record ID can verify an existing authorisation. A tool accepting a model-generated sentence saying “approved” gives the model more influence over what counts as approval.

The policy must also be executable at the boundary. A prompt saying “never send twice” is useful instruction, but it is weaker than a reliable action registry or external idempotency mechanism.

## State, receipts and retries

A **retry** repeats an operation after uncertainty or failure. It is often sensible for a read. For an action, it can duplicate effects. Suppose a credit is issued, but the acknowledgement is lost. Retrying without checking identity may create another credit.

**Idempotency** means that repeating the same identified operation does not repeat its business effect. In practice, this often needs a stable action identifier and cooperation from the system performing the effect. A local variable saying “already sent” disappears when its process stops and may be invisible to another worker.

An **execution receipt** records what the action service acknowledged. A statement generated by a model is not that receipt. Even a receipt may need interpretation: “request accepted” and “credit issued” are distinct statuses.

## Several components do not automatically make a better system

The course combines a scanner, several estimators, planners and a messenger. Splitting work can clarify responsibilities and permit specialised components. It also creates interfaces, timing dependencies and partial failures.

An **ensemble** combines predictions. It helps when components add useful complementary information under a validated combination rule. Three models can share an error, so counting them is not evidence of independent confirmation.

The local framework uses a fixed planner by default, although a model-selected planner also exists. Its ensemble calculation uses explicit fixed weights. These implementation details matter more than labels suggesting complete autonomy or learned combination.

## Remote services and ongoing operation

Calling a remote model crosses a network boundary. The service can be unavailable, loading or overloaded. A **cold start** occurs when capacity must initialise before handling work; loading model weights can contribute to the wait. Keeping capacity ready can improve responsiveness at an operating cost.

**Monitoring** observes behaviour over time. Logs can help diagnose program events. An organisational audit trail additionally needs understandable links among the request, sources, authorisation, actor, action and acknowledged outcome. Neither a stream of technical messages nor a colourful agent display establishes accountability.

## Bound the operating problem

Set limits on steps, time, cost and permitted actions. Define what happens when evidence is missing, sources conflict or a service fails. Allocate ownership of unresolved work rather than merely returning “error” to a screen.

The most appropriate design may be a fixed workflow with one model-mediated classification step. Choose autonomy when its added flexibility addresses a demonstrated need, and evaluate that need against the added burden.
