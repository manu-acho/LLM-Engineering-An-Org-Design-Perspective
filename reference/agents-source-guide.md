## A second engineering foundation

Part II is inspired by [Ed Donner's Agents course](https://github.com/ed-donner/agents), alongside the LLM Engineering course used for Part I. Ed's notebooks and reference applications provide the engineering examples and six-week progression. This guide adds explanations of the mechanisms and code, small independent examples, alternative designs and connections to business work and organisation design.

The links below use repository revision `542a7036c321a9308379507b06ce8d0deb370d5d`, which was publicly available when the guide was extended. The version identifies the code discussed; it is not a claim that every package, model name or hosting instruction remains current. [The current repository](https://github.com/ed-donner/agents) may contain changes.

## What was examined

The explanations use selected notebook source cells, reference-project configuration and application code paths. The named anchors are intended to make those paths inspectable. Coverage is selective: it does not imply that every cell, optional extension, community contribution, output file or generated application was examined equally.

Week 5 in this version includes Google ADK and A2A, AWS Strands, Pydantic AI, Microsoft Agent Framework, Agno and Mastra, followed by an orchestrated worker project. The [framework tour](../modules/13-agent-frameworks/04-framework-tour.md) explains that specific comparison. The course's short title is not used as an exhaustive framework inventory.

Lecture videos were not independently reviewed. Saved notebook outputs and generated project reports are not treated as fresh evidence of correctness, performance or successful deployment. No original notification, email, browser-automation, trading, sandbox execution or model-training workflow was run to prepare this extension.

The small Python examples in the new lessons are independent illustrations. They use fakes, in-memory records or simulation. They are distinct from framework integration code, which needs its own environment, dependencies, credentials, version checks and tests. Successful execution of a small example does not certify a production integration.

## Technical documentation and version boundaries

Selected technical distinctions were checked against primary documentation on 4 November 2026:

- [OpenAI Agents SDK](https://developers.openai.com/api/docs/guides/agents/sdk), [orchestration](https://developers.openai.com/api/docs/guides/agents/orchestration) and [guardrails and review](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals): runtime ownership, specialist calls, handoffs and check boundaries.
- [CrewAI processes](https://docs.crewai.com/en/concepts/processes): sequential and hierarchical coordination.
- [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence) and [interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts): saved state, thread scope and resumption.
- [ADK agents](https://adk.dev/agents/) and [Pydantic AI agents](https://ai.pydantic.dev/agents/): framework concepts alongside the inspected worker implementations.
- [A2A overview](https://a2a-protocol.org/latest/topics/what-is-a2a/): communication between agent services.
- [MCP architecture](https://modelcontextprotocol.io/docs/learn/architecture) and the [versioned HTTP authorisation specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization): capability interfaces and transport-level access boundaries.

Current documentation and the pinned course code may describe different package or protocol versions. The lessons identify the source implementation being discussed. They do not silently substitute newer APIs or claim that a current documentation example validates an older environment.

## Organisation-design foundation

The same six literature reviews support both parts of the guide. [Organisation design](https://github.com/manu-acho/org-design-as-code/blob/4e40b3b65360140d89e9581e4e668ef38ab77482/Enterprise-Software-as-Organisation/literature/Stream_01_Organisation_Design_Detailed_Review.md) examines division and integration; [coordination](https://github.com/manu-acho/org-design-as-code/blob/4e40b3b65360140d89e9581e4e668ef38ab77482/Enterprise-Software-as-Organisation/literature/Stream_02_Coordination_Theory_Detailed_Review.md) helps specify dependencies and shared understanding; [decision theory](https://github.com/manu-acho/org-design-as-code/blob/4e40b3b65360140d89e9581e4e668ef38ab77482/Enterprise-Software-as-Organisation/literature/Stream_03_Decision_Theory_Detailed_Review.md) locates premises, discretion and authority; [enterprise systems](https://github.com/manu-acho/org-design-as-code/blob/4e40b3b65360140d89e9581e4e668ef38ab77482/Enterprise-Software-as-Organisation/literature/Stream_04_Enterprise_Systems_Implementation_Transformation_Detailed_Review.md) broadens fit and implementation; [routines](https://github.com/manu-acho/org-design-as-code/blob/4e40b3b65360140d89e9581e4e668ef38ab77482/Enterprise-Software-as-Organisation/literature/Stream_05_Organisational_Routines_Detailed_Review.md) separates artefacts from recurrent work; and [technology in practice](https://github.com/manu-acho/org-design-as-code/blob/4e40b3b65360140d89e9581e4e668ef38ab77482/Enterprise-Software-as-Organisation/literature/Stream_06_Technology_Materiality_Organisation_Detailed_Review.md) connects features to actor-specific possibilities, use and outcomes.

These are the review syntheses consulted for the organisational interpretation. Their original articles have not all been independently re-read for this guide. The fictional Harbour applications are not empirical findings about AI performance, SAP implementations or any particular firm. The [literature guide](literature-guide.md) retains the distinctions and evidence limits.
